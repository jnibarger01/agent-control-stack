# ACS enforcement-evidence matrix

Purpose: make each ACS security invariant auditable. A control is **enforceable** only when every execution path that can
produce its side effect passes it, and a denial prevents that side effect. Status uses three states:

- **Specified:** the invariant is written down.
- **Implemented:** code enforces it on identified paths.
- **Verified:** a negative test shows a bypass attempt produces no side effect.

Scope: the Desktop Commander (DC) managed path and the Jace Commander (JC) lane in this repository, worktree
`feat/jc-security-phases-4-8`. Verification was run in the isolated build `jc-sec-build` (executor compiled with `tsc`, tests
run with `HOME` isolated). Items marked "not inspected" were not checked. Changes from the previous revision are marked **(Phase 10)**.

## Remaining (not done, with reasons)

1. **Row 4 and 5 in production:** ACS must expose an attempt-state query (or push), with a documented answer for `live`,
   `cancelled`, `expired`, and `superseded`. Then the DC runtime wires `attemptFence`. Until then the boundary is a
   tested mechanism that production does not use. Wiring it now would make every call fail closed, so it was not wired.
2. **Row 7 residual:** a passkey operator identity is still a registered credential, not an authenticated human session. The
   self-asserted opt-out remains available and audited.
3. **Row 10 keys:** choose a key holder outside the executor (for example approverd or ACS) and provision the key there.
4. **Row 11 triggers:** wire LoopTrace integrity failures and audit-append failures to `contain()`.
5. **Row 6 spawn sites:** prove each direct process spawn is unreachable from a tool call, or route it through the gate.
6. **Row 2 JC nonce store:** inspect and test the JC lane's capability verification and nonce persistence.
