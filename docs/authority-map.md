# ACS Authority Map

- **Status:** Accepted — describes current implementation plus explicitly labeled target hardening.
- **Scope:** Authority boundaries only. This document does not authorize any deployment, credential, or service change by itself; changes still go through their own review and, where applicable, an ADR.
- **Applies to:** Every privileged action requested through the gateway/MCP surface, a scheduled job, a worker, an engine adapter, or a future agent integration.
- **Baseline:** Written against `main` at commit `d0a5906` (2026-07-26). `MUST`, `MUST NOT`, `SHALL`, and `SHALL NOT` are normative. "Current" describes verified repository behavior at that commit, with file:line citations; "target" defines required hardening not yet in place. A current contradiction between the two is a migration requirement, not permission to weaken the target.

This document supersedes an earlier, unmerged draft of the same name (PR #10, branch `docs/acs-iii-phase1-authority`) that was written against a much older commit and described a "dedicated iii transport engine" plus "Hermes," "OpenClaw," "AgentMemory," and "Codex Swarm" as integration partners. None of those exist in this codebase — searching the full repository for `iii`, `AgentMemory`, or `Codex Swarm` as architectural components returns nothing. "Hermes" and "OpenClaw" appear only as registry actor-type fixtures in tests (`storage/migrations/002_agent_registry.sql:18-19,96,98`; `packages/work-items/src/state-machine.test.ts:758-759`) and, for `openclaw`, as one of several interchangeable external CLI binary names a local dev tool can shell out to (`packages/machine-controller/src/direct-agent.ts:8`). This rewrite drops that vaporware framing and describes the authority boundaries that actually exist in this repository today, with a target-hardening section clearly separated from and never presented as already-implemented behavior.

## 1. Authority rule

ACS (this repository) is the sole policy-decision, approval, and execution-authorization control plane for every privileged action it admits. No other component — a worker, an engine adapter, the scheduler, the secret broker, or a future conversational/orchestration surface — may originate that authority; each may only consume an authorization ACS already issued.

| Concern                                 | Exclusive authority                                                                        |
| --------------------------------------- | ------------------------------------------------------------------------------------------ |
| Human intent and approval               | Human, through an ACS-controlled approval surface                                          |
| Policy decisions                        | `packages/policy-gate`                                                                     |
| Work-item state and lifecycle           | `packages/work-items`' SQLite store (`SqliteWorkItemStore`)                                |
| Action approval records                 | ACS work-item store (exact action-hash binding)                                            |
| Attempt / lease / workspace authority   | ACS work-item store's attempt records (`packages/work-items/src/attempt.ts`)               |
| Command / engine execution authority    | ACS-persisted `CommandAuthority`, verified by `CommandBroker` and `EngineIsolationBackend` |
| Credential leasing to a running attempt | `packages/secret-broker` (principal-bound, ACS-shaped, currently unintegrated — see §8)    |
| Scheduled work-item creation            | `apps/scheduler`, itself only a caller of the same `create_work_item` policy-gate tool     |
| Final authoritative result              | ACS work-item store's terminal status, written inside the audit-chained transaction        |

"Exclusive authority" means another component may carry, cache, display, or propose the information, but may not replace the named authority. A worker's self-reported result is not a verified result. A scheduler firing is not itself a policy decision. A secret-broker lease is not a work-item approval. An engine's stdout is not audit evidence until captured through the engine-isolation boundary.

## 2. Privileged-action lifecycle (current)

| Question                           | Current answer                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Who may request it?                | Any caller registered as an actor (`storage/migrations/002_agent_registry.sql`) through the gateway/MCP surface (`apps/gateway/src/mcp.ts`, `apps/gateway/src/server.ts`) or `apps/scheduler`, via `packages/policy-gate`'s `create_work_item` tool. There is no actor-type restriction on who may _request_ work — see §8, gap DECIDE-01.                                                                                                                                                                                                                                                                            |
| Who evaluates it?                  | `packages/policy-gate` evaluates the requested action, with `packages/agentos-contracts` invoked first as a hard compatibility veto (`packages/policy-gate/src/contracts.ts:26-44`) — see §8, gap AGENTOS-01.                                                                                                                                                                                                                                                                                                                                                                                                         |
| Who approves it?                   | A human, through the gateway's approval path, granting an approval record bound to the work item's exact action hash. MCP identities are explicitly denied the `approve_work_item` tool (`apps/gateway/src/mcp.ts:22,207-217`).                                                                                                                                                                                                                                                                                                                                                                                       |
| Who claims and executes it?        | One worker claims an approved work item under a compare-and-swap lease (`packages/work-items/src/store.ts`), then an engine adapter (Codex, Claude) executes it inside the sandbox/engine-isolation boundary under a `CommandAuthority` rooted in the persisted attempt/lease/workspace record — not the caller's claim (`packages/work-items/src/attempt.ts:130-147`; `packages/engine-adapter/src/command-broker.ts:69-103`).                                                                                                                                                                                       |
| Who verifies the result?           | **Currently: nobody, before the result becomes terminal.** `submitWorkResult` (`packages/work-items/src/store.ts:2456-2458`) accepts the worker's own reported outcome and transitions the work item to a terminal status (`store.ts:2548-2552`) inside the same audit-chained transaction, with no independent verification gate in between. An independent verifier (`packages/verification/src/independent-verification.ts`) exists, enforces implementer/verifier engine-identity separation, and requires exact criteria coverage — but nothing calls it from the result-submission path. See §8, gap VERIFY-01. |
| Where is the authoritative record? | The SQLite work-item store: work item, policy decision, exact action hash, approval, attempt/lease binding, and terminal result, all written inside one transaction gated on a valid audit chain (`store.ts:3048-3060`).                                                                                                                                                                                                                                                                                                                                                                                              |

**Acceptance invariant:** if any answer above is missing or ambiguous, or represented only in a worker's self-report, the action is not authorized or complete. As of this baseline, terminal-result acceptance does not yet meet this invariant for the verification step — that is recorded as an open gap, not asserted as closed.

## 3. Request and execution path (current)

```text
MCP client / gateway caller / apps/scheduler
          │ create_work_item (via packages/policy-gate)
          ▼
        ACS policy-gate
 agentos-contracts veto (compat) → ACS policy → durable ledger
          │ approved work item + exact action hash
          ▼
   Human approval (gateway approval surface; MCP cannot self-approve)
          │
          ▼
   Worker claims (lease, compare-and-swap)
          │ attempt + lease + workspace allocation persisted
          ▼
   Engine adapter (Codex / Claude) via CommandBroker
 authority re-verified against persisted attempt/lease/workspace
          │
          ▼
   Sandbox / EngineIsolationBackend (bwrap + systemd scope)
 byte-capped, redacted stdout/stderr; fencing-token bound
          │ worker-reported outcome
          ▼
   submitWorkResult → terminal status written in audit-chained transaction
          │
          ▼
   (target, not yet wired) independent verification before terminal status
```

There is no separate message-routing or transport engine in this codebase; the gateway process and the worker/engine-adapter processes communicate directly through the SQLite-backed work-item store and its lease/claim primitives. If a dedicated routing or multi-agent orchestration layer is introduced later, it MUST be added as a transport-only component under this same authority rule (§1) — it may not gain policy, approval, or terminal-result authority merely by being on the delivery path.

## 4. Execution authority binding (current, not aspirational)

Unlike the superseded draft, which described a versioned execution envelope as future work, a materially equivalent binding already exists and is enforced:

- `packages/sandbox/src/engine-contracts.ts:71-107` — `engineIsolationRequestSchema` (`EngineIsolationRequest`), a `.strict()` schema binding `workItemId`, `attemptId`, `leaseId`, `workerId`, `fencingToken`, `authorization.hash`, `policyVersion`, `auditCorrelationId`, `idempotencyKey`, `workspace.allocationId`, plus the engine executable, args, network egress allowlist, and resource limits (including the output-byte cap — see the `extract/scheduler-hardening` branch (PR #23) for its coverage).
- `engine-contracts.ts:109-129` — `EngineIsolationAuthorityReceiptSchema`, the matching receipt a verifier must produce, bound to the same identifiers plus a `canonicalWorkspacePath` and `executionEvent{id, sequence, hash}`.
- `packages/work-items/src/attempt.ts:130-147` — `commandAuthoritySchema`, the persisted-state side of the binding: an attempt, lease, and workspace allocation joined and validated against what ACS actually recorded, not what a caller claims.
- `packages/engine-adapter/src/command-broker.ts:69-103,186-196` — `CommandAuthorityStore`/`storeBackedVerifier` call `store.getCommandAuthority(...)` (`store.ts:669` interface, `store.ts:1406` implementation) to re-derive authority from persisted state before allowing execution.
- `docs/adr/0014-engine-isolation-boundary.md` — the accepted decision record for this boundary, introduced in response to an independent security review's FAIL finding that engine execution was not equivalently isolated to the CommandBroker sandbox path.

The envelope MUST NOT (and, per the schemas above, structurally cannot without failing validation) let a worker or engine adapter widen its own scope, mint another envelope, self-approve, or claim itself authoritative — `EngineIsolationBackend.execute` (`packages/sandbox/src/engine.ts:106-112`) parses every request through `engineIsolationRequestSchema.parse`, which fails closed on any field outside the strict schema.

## 6. Non-negotiable rules

1. A worker does not self-approve or self-verify. A verified result requires a step this repository has built (`packages/verification`) but not yet wired into the write path — treat that gap as open, not covered by this rule's intent.
2. No component may create an undocumented bypass around policy-gate. The one _documented_ bypass, `agentos-contracts`' pre-policy veto, is itself flagged for removal (gap AGENTOS-01) — its existence does not license a second one.
3. Every privileged action has one authoritative work item, one policy decision, one exact action hash, one approval record (if required), and one terminal result.
4. Audit persistence failure blocks further privileged mutation (`store.ts:3050`); it does not fall back to un-audited writes.
5. Retries and clones do not create new authority from nothing — they are append-only lineage operations that re-run policy and re-require approval (`docs/architecture.md`, "Retry and clone are append-only lineage operations").
6. Engine execution authority is re-derived from persisted attempt/lease/workspace state on every check (`getCommandAuthority`), never trusted from a caller's claim.
7. Worker success claims are inputs to (eventual) verification, not the verdict, even though the write path does not yet enforce this — see gap VERIFY-01.
8. A secret-broker lease is scoped to one principal (worker + work item + attempt + engine) and is not a general-purpose credential store.
9. If a dedicated transport/routing layer is ever introduced, it inherits none of the authorities in §1 merely by sitting on the delivery path.

## 7. Threat scenarios and required behavior (grounded in current code)

| Scenario                                                                                         | Required / current behavior                                                                                                                                                                                                                                                                                                                                                                                            |
| ------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A worker submits a forged or overly optimistic success result**                                | **Current gap.** `submitWorkResult` accepts the worker's own outcome and writes it as terminal (`store.ts:2456-2552`) with no independent verification call. `packages/verification`'s `runIndependentVerification` exists and would close this if wired in — see gap VERIFY-01. Until then, treat any terminal `succeeded` status as worker-reported, not independently verified.                                     |
| **A scheduler process races another and tries to double-create a work item for the same firing** | Addressed by the `extract/scheduler-hardening` branch (PR #23): a DB-enforced `UNIQUE(schedule_id, scheduled_firing_time)` constraint plus a transactional claim/complete lifecycle replaces the prior list-scan idempotency check. Prior to that fix, this was a real TOCTOU race.                                                                                                                                    |
| **The `agentos-contracts` compatibility veto is itself compromised or buggy**                    | Fail-closed by construction (it can only deny, not grant, admission) — but it still runs _before_ ACS's own policy evaluation, meaning ACS policy never gets a chance to allow something the legacy layer denies incorrectly. This is availability risk, not an authority-escalation risk, but it is exactly the kind of undocumented pre-policy dependency gap AGENTOS-01 flags for removal.                          |
| **A secret-broker lease is requested by an unbound caller**                                      | Structurally prevented — `LeaseRequest` requires a `LeasePrincipal` (workerId/workItemId/attemptId/engineId); there is no anonymous-lease code path.                                                                                                                                                                                                                                                                   |
| **An engine tries to exceed its output-byte cap, including via multibyte UTF-8**                 | Enforced at the raw-buffer level in `captureChunk` (`packages/sandbox/src/linux.ts:689-706`), shared by both the CommandBroker sandbox and `EngineIsolationBackend`; a multibyte character split by the cap cannot inflate the accounted byte count past the configured limit. Regression coverage for the `EngineIsolationBackend` path specifically was closed by the `extract/scheduler-hardening` branch (PR #23). |
| **The audit store cannot persist a write**                                                       | `store.ts:3050` throws `audit_chain_invalid` and blocks the write before any state or audit mutation is committed; ACS does not fall back to unaudited persistence.                                                                                                                                                                                                                                                    |
| **An MCP identity attempts to approve its own work item**                                        | Explicitly denied: `apps/gateway/src/mcp.ts:22,207-217` returns a `-32002` JSON-RPC error for `approve_work_item` regardless of caller identity.                                                                                                                                                                                                                                                                       |
| **A worker's lease or fencing token is stale or reused**                                         | `getCommandAuthority` re-derives authority from the persisted attempt/lease/workspace record on every check (`command-broker.ts:69-103`); a stale claim fails re-verification rather than being trusted from the caller.                                                                                                                                                                                               |

## 8. Known gaps and target hardening (not yet enforced)

These are recorded as migration requirements, not permission to claim they're already done, and not a commitment to a specific future integration (in particular: no dedicated routing/transport engine, and no specific third-party conversational-agent integration, is planned or assumed by this document).

| ID             | Current implementation fact                                                                                                                                                                                                                                                                                                                                                                                                                        | Target-architecture gap                                                                                                                                                                                           | Suggested remediation                                                                                                                                                                                                      |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **VERIFY-01**  | `submitWorkResult` writes a worker-reported outcome as terminal with no verification gate (`store.ts:2456-2552`). `packages/verification/src/independent-verification.ts` implements the missing check (implementer/verifier identity separation, exact-criteria coverage) but is not called from any other package — zero references outside its own package, and no other `package.json` depends on it.                                          | A verified result should require ACS-run verification before a terminal `succeeded` status is recorded; a worker's self-report should remain provisional until then.                                              | Wire `runIndependentVerification`/`workItemOutcomeForVerdict` into `acceptResultInTransaction` (or a new step ahead of it) so terminal status is verifier-derived, not worker-derived, for the risk tiers that require it. |
| **AGENTOS-01** | `packages/policy-gate/src/contracts.ts:26-44` still runs `agentos-contracts`' `validateEnvelope`/`applyRiskPolicy`/`route` as a hard veto before ACS's own policy evaluation runs; `packages/agentos-contracts/README.md` calls this "an acknowledged migration gap, not the target architecture."                                                                                                                                                 | ACS policy-gate should be the sole policy authority; compatibility code may supply evidence but should not gate admission on its own.                                                                             | Remove the hard-veto dependency in a separately reviewed migration, per the `agentos-contracts` README's own stated plan.                                                                                                  |
| **SECRET-01**  | `packages/secret-broker` implements principal-bound, use-accounted credential leasing, but no app (`apps/*`) imports it and no other package depends on `@agent-control-stack/secret-broker`; its own comments note its audit events are "intentionally not wired into the real hash-chained `audit_events` table" yet.                                                                                                                            | Any credential handed to a running attempt should flow through a leased, principal-bound, audited path rather than ambient environment configuration.                                                             | Wire secret-broker leasing into the worker/engine-adapter attempt path, and route its audit events into the canonical `audit_events` chain (per ADR 0011) rather than a separate log.                                      |
| **DECIDE-01**  | There is no actor-type restriction on who may request work through `create_work_item` — any registered actor (`HUMAN`/`SYSTEM`/`AGENT`/`SERVICE`) can. There is also no equivalent, on current `main`, of a "connector alias requires a registered HUMAN actor" check; a prior draft of this document cited `apps/gateway/src/connector.ts` for that behavior, but that file never existed on `main` — it only ever existed on an unmerged branch. | If a future surface needs to restrict _who may originate_ a request (as opposed to who may _approve_ one, which is already gated to humans), that restriction does not currently exist and should not be assumed. | Do not build against the assumption that request-origination is actor-type-restricted today; if that restriction is needed, it must be added and tested, not inferred from stale documentation.                            |
