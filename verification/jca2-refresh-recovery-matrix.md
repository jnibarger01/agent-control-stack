ACS new process loads persisted credentials containing predecessor refresh token/device identity and recovers via server envelope.
5. **Original request ID used:** Required for JC recovery (`store.js`/tests). ACS uses proof-bound identity rather than request ID.
6. **Exact successor recovered:** Asserted in ACS crash-recovery and multi-process tests; asserted in JC SEC-24 and dc-mcp gateway recovery test.
7. **No second successor created:** Asserted by identical successor hashes/tokens across retries/processes and DB checks showing one rotation (`previous_refresh_token_hash` remains original, current hash equals recovered successor).

### Explicit conflicting assumptions to track

1. **Request ID vs proof-only recovery identity:** JC requires matching `refresh_request_id` for exact-successor recovery; ACS has no request-id field. Assuming one mechanism implies the other is incorrect.
2. **Envelope consumption model:** JC ties recoverability to consumed-row request metadata and successor liveness; ACS ties it to envelope row validity and non-superseded successor hash. "Consumed envelope" is not represented identically.
3. **Invalid/wrong key handling:** ACS adversarial policy avoids revocation on invalid proof (anti-DoS) but revokes on genuine replay; JC treats DPoP key/JKT mismatch during refresh rotation as family-revoking reuse/failure in covered cases. Policies are intentionally different and must not be "normalized" by weakening checks.
4. **Revocation granularity and fields:** ACS clears device token hashes/expiries and recovery envelopes on revocation/replay paths; JC revokes family rows and device state in store. Any cross-component audit must map field names/tables.
5. **Client persistence boundaries:** JC CLI depends on `pending-refresh.json` + secret store metadata for restart replay of request id; ACS runtime refresh depends on persisted credentials and server envelope for crash-before-persist recovery. "Pending refresh" persistence is not symmetric.
6. **Default 120s window configuration:** Same value, different env/config names and test overrides (`ACS_DEVICE_REFRESH_RECOVERY_WINDOW_SECONDS`/recovery config vs `JC_REFRESH_RECOVERY_WINDOW_S`/`RECOVERY_TTL_S`/`EDGE_TEST_RECOVERY_TTL_S`). Misconfiguration risk if assumed shared.
7. **System scope:** Mandatory scenarios apply across JC and ACS subsystems present in this repo; evidence must be interpreted per subsystem, not assumed globally proven by one implementation.
